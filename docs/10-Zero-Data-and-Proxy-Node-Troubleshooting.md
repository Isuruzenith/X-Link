# 10 — Zero-Data & Proxy Node Troubleshooting: Edge Cases, Protocol Mismatches & Solutions

**Navigation**: [[00-Home-MOC]] | **Prev**: [[08-User-Guide-and-FAQ]] | **Related**: [[01-Architecture-Overview]], [[05-Rust-Backend-Architecture]], [[06-IPC-Bridge-and-Data-Contracts]]

## 1. Executive Summary & Purpose

In restricted ISP environments—such as Sri Lankan mobile carriers (Dialog, Mobitel, Airtel) offering zero-rated or education-package bundles (Zoom, MS Teams, Office 365, Work & Learn packages)—users leverage **Bug Host / Zero-Data SNI Spoofing** to route non-whitelisted internet traffic through remote proxy VPS servers (e.g., VLESS/VMess/Trojan over WebSocket/gRPC).

While specialized tools like **NetMod Syna** connect effortlessly in these environments, modern core engines like **sing-box v1.13+** enforce strict RFC standards, modern TLS certificate validation, and explicit protocol negotiation. Consequently, importing raw zero-data share links into standard sing-box clients frequently leads to silent connection failures, TLS certificate aborts, ALPN protocol negotiation mismatches, and DNS bootstrap deadlocks.

This document serves as the authoritative post-mortem, architectural reference, and operational playbook for all real-world proxy node failures encountered, their underlying root causes, comparison with NetMod Syna, and the automated solutions implemented in **X-Link**.

## 2. Issue 1: TLS x509 Certificate Verification Failure (SNI Spoofing)

### 2.1 Failure Symptom & Raw Sing-box Log
```text
DEBUG outbound/urltest[auto]: outbound One Piece SG-Prabathya unavailable: tls: failed to verify certificate: x509: certificate is valid for azure.ezgateway.net, not cloud.microsoft
ERROR connection: open connection to www.gstatic.com:443 using outbound/vless[One Piece SG-Prabathya]: tls: failed to verify certificate: x509: certificate is valid for azure.ezgateway.net, not cloud.microsoft
Startup error: Connection failed: HTTP proxy probe failed: node/outbound/config did not carry HTTPS traffic (error sending request to health check endpoints)
```

### 2.2 Mechanism & Root Cause
In a Zero-Data network configuration:
1. **SNI (Server Name Indication)** is set to an ISP-whitelisted domain (e.g., `cloud.microsoft`, `teams.microsoft.com`, `zoom.us`, or `aka.ms`) so the telecom firewall / deep packet inspection (DPI) allows the TCP connection through.
2. **Transport Host Header** is set to the actual remote VPS domain (e.g., `azure.ezgateway.net`).
3. **The Problem**: When the TLS ClientHello reaches the remote server (`azure.ezgateway.net`), the server returns its valid SSL certificate issued by Let's Encrypt / DigiCert specifically for `azure.ezgateway.net`.
4. Sing-box performs strict x509 certificate validation against the spoofed SNI (`cloud.microsoft`). Because `azure.ezgateway.net != cloud.microsoft`, sing-box immediately terminates the TLS connection.
5. Most share URIs generated by proxy management panels omit `&allowInsecure=1` or `&insecure=1`.

### 2.3 Why NetMod Syna Succeeded
NetMod Syna is specifically architected for ISP bug host tunneling. By default, it sets `InsecureSkipVerify: true` on all TLS connections, silently ignoring x509 certificate mismatches when an SNI differs from the server domain.

### 2.4 Automated Solution in X-Link
X-Link implements **dual-layer auto-detection** so users never have to manually edit nodes or toggle insecure settings:

1. **Import Layer (`src-tauri/src/config/adapters/raw_uri.rs`)**:
   When parsing raw URIs (`vless://`, `vmess://`, `trojan://`):
   ```rust
   // If SNI is spoofed for ISP zero-data / bug host (e.g. SNI differs from the transport host),
   // auto-detect on import so nodes connect seamlessly out-of-the-box:
   if !is_insecure && security != "reality" {
       if let Some(sni_val) = sni {
           let sni_clean = sni_val.trim().to_lowercase();
           if let Some(host_val) = query_params.get("host") {
               let host_clean = host_val.trim().to_lowercase();
               if !sni_clean.is_empty()
                   && !host_clean.is_empty()
                   && sni_clean != host_clean
                   && !host_clean.ends_with(&format!(".{}", sni_clean))
                   && !sni_clean.ends_with(&format!(".{}", host_clean))
               {
                   is_insecure = true;
               }
           }
       }
   }
   ```
2. **Runtime Generation Layer (`src-tauri/src/config/generator.rs`)**:
   Protects existing imported nodes without requiring re-import. Before writing sing-box JSON configuration, X-Link inspects the outbound. If `transport.host` matches the server host domain, but `tls.server_name` (SNI) is different (and not Reality), X-Link injects `"insecure": true` dynamically into the sing-box outbound configuration.

## 3. Issue 2: WebSocket EOF Disconnect via ALPN `h2` Negotiation (Protocol Mismatch)

### 3.1 Failure Symptom & Raw Sing-box Log
```text
INFO outbound/vless[One Piece SG-Prabathya]: outbound connection to cp.cloudflare.com:443
DEBUG outbound/urltest[auto]: outbound One Piece SG-Prabathya unavailable: EOF
ERROR connection: open connection to cp.cloudflare.com:443 using outbound/vless[One Piece SG-Prabathya]: EOF
```

### 3.2 Mechanism & Root Cause
1. Many proxy subscription links indiscriminately include `alpn=h2%2Chttp%2F1.1` in raw URIs, even for `type=ws` (WebSocket) or `type=httpupgrade`.
2. When sing-box initiates the TLS handshake, it advertises both `h2` (HTTP/2) and `http/1.1` in the ALPN extension of the TLS ClientHello.
3. If the remote endpoint or CDN reverse proxy (e.g., Cloudflare, AWS CloudFront, Nginx, Caddy) supports HTTP/2, it negotiates **`h2`** as the application protocol.
4. **The Critical Protocol Conflict**:
   - Standard WebSocket (RFC 6455) is exclusively an **HTTP/1.1 Upgrade** mechanism (`Upgrade: websocket`, `Connection: Upgrade`).
   - Sing-box's WebSocket dialer is based on standard Go `gorilla/websocket` / `net/http` WebSocket client implementations, which do not implement RFC 8441 (WebSockets over HTTP/2 Extended CONNECT).
   - Once the TLS tunnel is established with ALPN `h2`, sing-box transmits ASCII HTTP/1.1 text (`GET /path HTTP/1.1\r\nHost: ...`).
   - The remote HTTP/2 server expects binary HTTP/2 frames (`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` followed by binary `SETTINGS` frames). Seeing invalid ASCII data on an HTTP/2 session, the server terminates the connection with `RST_STREAM` / `GOAWAY` / TCP FIN, reported by sing-box as **`EOF`**.
5. **HTTPUpgrade Transport Variant**:
   - For `httpupgrade` transport, the remote server sends an HTTP/2 binary SETTINGS frame (`\x00\x00$\x04\x00\x00...`). Sing-box's HTTP/1.1 response parser attempts to parse these binary bytes as text and throws:
     `malformed HTTP response "\x00\x00$\x04\x00\x00\x00\x00\x00\x00\x05\x00\x10..."`

### 3.3 Live Verification Benchmark
Direct reproduction against live server `azure.ezgateway.net`:
- **With ALPN `["h2", "http/1.1"]`**: Sing-box fails with `502 Bad Gateway` and `connection: ... EOF`.
- **With ALPN `["http/1.1"]` (or stripping `h2`)**: Handshake succeeds with `HTTP/1.1 101 Switching Protocols` -> `HTTP/1.1 204 No Content` proxy traffic established immediately.

### 3.4 Automated Solution in X-Link
In `src-tauri/src/config/generator.rs`:
```rust
// WebSocket and HTTPUpgrade transports use HTTP/1.1 Upgrade mechanisms. If TLS negotiates
// "h2", the server expects HTTP/2 binary framing while the client sends HTTP/1.1 ASCII text,
// causing the connection to fail with EOF or malformed HTTP response. Strip "h2" so negotiation
// uses HTTP/1.1.
let transport_type = obj
    .get("transport")
    .and_then(|t| t.get("type"))
    .and_then(|t| t.as_str())
    .map(str::to_string);
if matches!(transport_type.as_deref(), Some("ws" | "httpupgrade")) {
    if let Some(tls) = obj.get_mut("tls").and_then(Value::as_object_mut) {
        if let Some(alpn) = tls.get_mut("alpn").and_then(Value::as_array_mut) {
            alpn.retain(|v| v.as_str() != Some("h2"));
            if alpn.is_empty() {
                *alpn = vec![Value::String("http/1.1".to_string())];
            }
        }
    }
}
```
*Note: Protocols requiring `h2`—such as gRPC, native HTTP/2 (`http`), and TCP Reality Vision—preserve explicit `h2` completely.*

## 4. Issue 3: DNS Deadlock & Remote DNS Timeout on Zero-Data Networks

### 4.1 Failure Symptom & Raw Sing-box Log
```text
dial udp [2402:4000::2]:53: i/o timeout
dial tcp 1.1.1.1:853: i/o timeout
Startup error: Connection failed: HTTP proxy probe failed: node/outbound/config did not carry HTTPS traffic (error sending request to health check endpoints)
```

### 4.2 Mechanism & Root Cause
1. On restricted telecom networks (Dialog Sri Lanka, etc.), all raw outbound UDP and TCP traffic is blocked by default, with only specific ports (443) allowed for whitelisted SNIs.
2. In TUN mode, if sing-box is configured with remote DoT (`tls://1.1.1.1:853`) or upstream UDP port 53:
   - Sing-box cannot reach `remote-dns` because the proxy connection is not yet established.
   - Sing-box cannot establish the proxy connection because it needs to resolve the proxy server's domain (`azure.ezgateway.net`).
   - The circular dependency results in an `i/o timeout` deadlock, causing startup probes to fail.

### 4.3 Automated Solution in X-Link

1. **Pre-Resolution & Static Injections (`src-tauri/src/config/generator.rs`)**:
   Before compiling the sing-box configuration, X-Link pre-resolves proxy server domains using OS network APIs (`crate::config::resolve_host_ip_addrs`) and injects static A and AAAA answers into `dns.rules` using action `predefined`:
   ```json
   {
     "domain": ["azure.ezgateway.net"],
     "action": "predefined",
     "answer": [
       "azure.ezgateway.net. 300 IN A 52.74.19.235",
       "azure.ezgateway.net. 300 IN AAAA 2406:da18:bcc:2800:c3e7:302d:e8bb:fabf"
     ]
   }
   ```
2. **Direct IP Outbound Assignment**:
   The outbound `server` field is pre-populated with the chosen IP address, while `tls.server_name` preserves the spoofed SNI or host domain.
3. **System Proxy Mode DNS Decoupling**:
   In System Proxy mode, remote domain names are resolved remotely by the proxy server over SOCKS5/HTTP CONNECT. X-Link decouples the local DNS server from remote DoT, routing internal DNS strictly via `local-dns` with direct detour.
4. **Graceful Routing Mode Fallback (`src-tauri/src/commands/proxy.rs`)**:
   If TUN mode startup probe times out due to packet drops on restrictive zero-data networks, X-Link automatically rolls back to System Proxy mode without disrupting the user session.

## 5. Issue 4: WebSocket Early Data (`?ed=2048`) & Path Preservation

### 5.1 Problem
When 0-RTT WebSocket early data is enabled on Cloudflare / reverse proxies, the path contains a query parameter:
`/azure?ed=2048`
If the entire string is passed as `path`, sing-box treats it as the raw HTTP path, but sing-box requires `max_early_data: 2048` to activate 0-RTT early data. If the query string is clumsily stripped, other necessary URL parameters are lost.

### 5.2 Solution
X-Link uses `parse_ws_path_and_early_data`:
```rust
pub fn parse_ws_path_and_early_data(raw_path: &str) -> (String, Option<u32>)
```
It extracts `ed=<number>` into `max_early_data` (and `early_data_header_name: "Sec-WebSocket-Protocol"`), cleans the path, and preserves all other query parameters intact.

## 6. Issue 5: Schema Strictness & Rule Action Invariants (sing-box v1.13+)

### 6.1 Problem
Sing-box v1.13+ rejects legacy v1.11 / Clash-style route directives:
- `"outbound": "block"` causes a fatal schema check error.
- `"outbound": "dns"` is rejected.
- Adding `domain_resolver` or dial options to selector or URL-test outbound groups causes process crash on boot.

### 6.2 Solution
In `src-tauri/src/config/rules.rs`:
- Custom block rules compile to `{"action": "reject"}`.
- DNS capture compiles to `{"protocol": "dns", "action": "hijack-dns"}`.
- Selector groups and URL-test outbounds are strictly excluded from dial fields and resolvers.

## 8. Developer & Maintenance Playbook

When adding or updating proxy protocols in X-Link:
1. **Never blanket-mutate ALPN**: Only strip `h2` for transports that strictly require HTTP/1.1 (`ws`, `httpupgrade`). Keep `h2` for `grpc`, `http`, and TCP Reality.
2. **Never disable uTLS on Reality**: Reality handshakes require valid client fingerprints (`chrome`).
3. **Always Run Offline Verification First**:
   ```powershell
   cargo test --manifest-path src-tauri/Cargo.toml
   npm test
   ```
4. **Validate Against Bundled Sing-box Binary**:
   Run `sing-box check -c <config.json>` to guarantee that sing-box v1.13.14 accepts the schema before activating candidates.
